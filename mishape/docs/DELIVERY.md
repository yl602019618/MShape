# MiShape 0.1：使用与技术交付说明

## 交付范围

MiShape 将 polygon 车辆造型组织为两套工作台：已有模型的参数塑形，以及由尺寸与构型生成模型。它复用 `aeroshape` 中已有的车辆曲面与组件基础设施，使用独立的 `mishape.app`、界面、数据目录和 8010 端口；不要求启动旧应用。

交付包含本地 WebGL2 三维界面、两个真实 Porsche 素材包、17 个塑形驱动、7×3×4 粗控制笼、参数生成、组件选择/隔离/展开、模型与工程导出、最多 50 个变体的批量探索。生成器基于人工构建的概念几何，不是汽车厂商的原始 CAD，也不是经过制造生产认证的模型。

## 本地启动与保存

需要 Python 3.11+ 和支持 WebGL2 的桌面浏览器。macOS 可双击 `start.command`；终端也可在包含 `mishape` 与 `aeroshape` 的项目根目录运行：

```sh
bash mishape/start.sh
# 仅检查目录与依赖
bash mishape/start.sh --check
```

打开 [http://127.0.0.1:8010](http://127.0.0.1:8010)。启动器依次复用父级项目、本目录的 `.venv`；缺少环境时创建本目录的 `.venv`，依赖缺失时安装 `requirements.txt`。首次安装需要访问 Python 包源；已准备好的运行环境不需要 Blender、bpy、Node.js、GPU 云服务或外部 API Key。静态页面和内置车辆由本机服务提供。

启动器固定绑定 `127.0.0.1`，不开放局域网监听；重复启动时可复用已运行的 MiShape 实例。启动终端中的 `Ctrl+C` 停止服务。端口被其他软件占用时启动会报错，不会强制终止其他进程。

默认模型与批量结果写入 `mishape/.state`，浏览器会记住上次设计的模型标识与编辑配方。`MISHAPE_STATE` 环境变量可以指定其他存储目录。建议把阶段成果下载为 JSON 工程，不要将浏览器缓存当作唯一存档。删除 `.state` 会使依赖该目录的会话与批量结果失效。

## 模型塑形工作台

### 导入与坐标

内置素材包括 Porsche 911 930 Turbo 和 Carrera 4S。外部导入接受 OBJ、STL、PLY、GLB、MiShape JSON，单文件上限 180 MB；模型验证上限为 150 万顶点、200 万三角面。非常大的模型会增加传输、控制笼绑定和界面渲染成本，上限不是流畅性能保证。

内部采用右手坐标：米制，X 沿车长、车头朝 −X，左侧为 +Y，向上为 +Z，地面为 Z=0。导入时声明源文件的向上轴、车头轴，并选择「米」「毫米」或「按已知车长校准」。车头与向上方向必须正交。

Blender 文件不由普通导入窗口直接打开：所提供两辆车已经离线预处理。其他 Blender 素材应先导出 GLB，或由离线转换管线新增素材。OBJ 导入保留源多边形与顶点顺序、正负索引、对象/组件分组；STL/PLY/GLB 的通用导入以三角面构成编辑拓扑，组件依据源对象节点保留；它没有自动推断出完整生产零件的保证。

### 自动测量与校准

工作台显示车长、车宽、车高、轴距、前后悬、风挡、引擎盖、车尾与姿态等几何测量，并显示测量方法与置信度。直接包围盒测量、素材关键点、命名组件推断和自动估计是不同的数据来源。对角度使用 XZ 中心纵剖面中的关键点弦线，不表示每一个 polygon 的局部法向角。

内置 Porsche 的真实标定尺寸未知，930 按约 4.30 m、Carrera 按约 4.43 m 的车长统一缩放。宽、高、轴距等毫米量随此假设确定，均为需要校准的估计。可在「测量与校准」面板输入已知当前车长，统一缩放当前设计并建立新的基准；原模型和原配方仍留在本地缓存；在测量面板选择关键点并输入米制 X/Y/Z，可以校准轮轴或玻璃等位置。关键点编辑不会单独完成整车尺度标定。

### 17 个关键造型驱动

全部塑形滑块默认为 0，输入是相对基准模型的增量。长度输入单位为 mm，角度为度。每次运算从同一基准网格求值，避免连续拖动产生累积误差。多个驱动同时作用时，它们是局部位移场的组合；结果应以更新后的几何测量为准，不能把滑块视为满足独立尺寸约束的精确逆解。

| 参数 / API key | 增量范围 | 定义 |
| --- | --- | --- |
| 整体长度 / `total_length` | -600…600 mm | 绕车身中心整体伸缩；轴距与前后悬按比例变化。 |
| 轴间车身长度 / `vehicle_length` | -500…500 mm | 拉伸前后轴之间的车身；前后悬保持长度，轴距随之变化。 |
| 车宽 / `vehicle_width` | -300…300 mm | 左右对称改变整体车宽，车轮随轮距平移并保持形状。 |
| 车高 / `vehicle_height` | -250…300 mm | 以地面为基准改变车身高度；保留轮胎直径。 |
| 前悬 / `front_overhang` | -300…300 mm | 前轴前方的车身向车头延伸；前轴保持位置。 |
| 后悬 / `rear_overhang` | -300…300 mm | 后轴后方的车身向车尾延伸；后轴保持位置。 |
| 接近角 / `approach_angle` | -15…15 ° | 前轮地面接触点至前保险杠下缘连线与地面的角度变化。 |
| 前风挡角 / `windscreen_angle` | -15…15 ° | 前风挡下缘至上缘在XZ侧视平面内与地面的锐角变化。 |
| 后风挡角 / `backlight_angle` | -15…15 ° | 后风挡上缘至下缘在XZ侧视平面内与地面的锐角变化。 |
| 尾厢盖高度 / `decklid_height` | -150…150 mm | 车尾盖板区域的垂直位移。 |
| 车尾收窄 / `rear_end_tapering` | -200…200 mm | 正值减小车尾总宽度，负值加宽。 |
| 座舱收窄 / `greenhouse_tapering` | -200…200 mm | 正值减小车顶宽度，向腰线平滑过渡。 |

| 车身离地高度 / `ride_height` | -100…150 mm | 车身相对车轮上下移动；轮胎接地点保持不动。 |
| 车身俯仰 / `vehicle_pitch` | -3…3 ° | 绕横向轴旋转车身；正值为车头抬升，轮胎仍接地。 |
| 后扩散器角 / `diffusor_angle` | -15…15 ° | 尾部底板与地面夹角的变化；以底板前端为支点。 |

### 粗 polygon 控制笼

控制笼包含 7×3×4 共 84 个控制点，分别沿车长、车宽、车高布置。关键参数驱动和手动控制点都形成位移场，通过局部三次插值作用于基准顶点；不会在每次拖动时重新划分 polygon。

在界面打开控制笼后，按住 `Shift` 拖动控制点；也可以从列表选点，输入 X/Y/Z 位移。界面单位是 mm，API 的 `delta` 单位是 m，单轴位移限制 ±350 mm。左右对称开关会配对左右控制点并约束中心面；保持车轮开关将已识别轮组作为刚体平移，保护轮胎与轮毂形状。对于未命名或未分离轮组的自有模型，刚性保护可能不可用，需先在外部工具中拆分并命名。

撤销、重做及恢复基准用于管理当前塑形配方。保存工程保留当前状态，不保存整个撤销历史。生成器参数有独立的模型生成流程，塑形的撤销栈不是生成过程的完整版本历史。

### 三维检查与组件

左键拖动旋转，右键拖动平移，滚轮缩放。可切换前/侧/顶/后等视角、显示线框或位移，并通过双视图检查基准与结果。展开效果仅用于观察组件关系，不会把展开位移写入导出几何。

左侧组件列表和模型点击可选择组件，支持隔离显示、恢复全部、展开观察，以及导出单一选中组件。内置 Porsche 的组件由原对象/材质整理而来，生成车的组件由构造过程提供；这是一套已有组件标签的操作工具，当前版本没有任意未知车模的自动生产级零件分割、切割面设计或标签刷重标注。

## 参数生成工作台

选择溜背 `fastback`、三厢 `sedan`、旅行车 `estate`、两厢 `hatchback` 或 SUV `suv`，再调整尺寸、座舱、车头、车尾、轮组和底部造型。该工作台输入通常为绝对物理值，长度单位是 m；与塑形工作台的 mm 增量不同。生成完成后可以切回模型塑形，继续使用控制笼、测量、组件和批量探索。

当前界面公开 28 个连续参数，另有 4 组组件选型。参数之间存在耦合约束，单个滑块值在范围内不代表组合一定有效。无效组合返回具体错误，不会默默改写为另一组参数。

| 生成参数 / API key | 范围 | 定义 |
| --- | --- | --- |
| 整车长度 / `length` | 3.9…5.35 m | 轴距与前后悬之和；前后悬按前悬占比分配。 |
| 车身宽度 / `width` | 1.7…2.1 m | 车身外板的基础宽度，不含后视镜；实测包络在质量报告中。 |
| 车顶高度 / `height` | 1.32…1.88 m | 轮胎接地点到车顶中心冠顶控制点的高度。 |
| 轴距 / `wheelbase` | 2.45…3.2 m | 前后轮轴心间距；保持整车长度时会改变两端悬长。 |
| 前悬占比 / `front_overhang_ratio` | 0.38…0.62 ratio | 前悬占总悬长的比例；前悬与后悬的实际值自动计算。 |
| 底板离地 / `ride_height` | 0.13…0.3 m | 中部底板中心名义离地高度；不是整车最小离地间隙。 |
| 轮距 / `track` | 1.5…1.88 m | 左右轮组中心距，前后轴相同。 |
| 轮胎半径 / `wheel_radius` | 0.3…0.43 m | 轮胎和轮毂径向等比变化，轮拱随之适配。 |
| 胎宽 / `tyre_width` | 0.19…0.29 m | 轮组轴向宽度；必须与轮距、车宽相容。 |
| 车顶控制段 / `cabin_length` | 1.02…2.55 m | 前风挡上缘到后风挡上缘的纵向距离。 |
| 前风挡角 / `windscreen_angle` | 25…65 ° | 中心纵剖面上下缘弦线与水平面的夹角。 |
| 后风挡角 / `backlight_angle` | 22…82 ° | 后风挡中心剖面弦线角；不等于每个面片的法向角。 |
| 车顶冠高 / `roof_crown` | 0.01…0.18 m | 车顶中心相对前缘的冠高。 |
| 车顶后缘落差 / `roof_rear_drop` | -0.12…0.2 m | 正值降低后缘，负值使后缘高于前缘。 |
| 座舱内倾 / `greenhouse_taper` | 0…18 ° | 腰线以上向内倾斜，左右对称。 |
| 前盖后缘高度 / `hood_height` | 0.9…1.18 m | 前风挡下缘中心高度，与风挡角共同决定座舱前缘。 |
| 前盖冠高 / `hood_crown` | 0…0.06 m | 前盖中部的平滑拱高，保持端部衔接。 |
| 车头收窄 / `front_taper` | 0…0.2 ratio | 从前轴向车头的连续平面收窄比例。 |
| 后甲板高度 / `decklid_height` | 0.84…1.28 m | 后风挡下缘中心高度，受后车顶和腰线约束。 |
| 尾箱平台长度 / `decklid_length` | 0…0.85 m | 0 为连续尾门；正值构成独立尾箱平台。 |
| 车尾收窄 / `rear_taper` | 0…0.18 ratio | 从后轴至车尾的平滑单侧收窄比例。 |
| 后肩外扩 / `rear_shoulder` | 0…0.05 m | 后翼子板单侧外扩量，会增加实测车身宽度。 |
| 尾门角 / `tailgate_angle` | 55…89 ° | 尾门中心上下缘弦线角，独立于后玻璃角度。 |
| 尾门下缘 / `tailgate_lower_height` | 0.62…1.02 m | 尾门与后围板的中心连接高度。 |
| 后腰线高度 / `rear_belt_height` | 0.82…1.16 m | 后玻璃附近的侧面腰线；须低于玻璃下缘。 |
| 扩散器角 / `diffuser_angle` | 2…18 ° | 底部控制段入口到出口的中心弦线角。 |
| 扩散器长度 / `diffuser_length` | 0.3…0.82 m | 车尾底部渐升段的长度。 |
| 扩散器宽度 / `diffuser_width` | 0.85…1.6 m | 左右平滑过渡的底板控制带宽度。 |

组件选型由 `mirror_style`、`spoiler_style`、`front_style`、`diffuser_style` 指定，可用选项通过 `/api/bootstrap` 的 generation schema 获取。选项是适配当前概念几何的作者构建变型，不表示 OEM 零件的真实互换性。

主要耦合约束包括：前悬 `(length-wheelbase)×front_overhang_ratio` 应为 0.68–1.12 m，后悬应为 0.55–1.18 m；轮距加胎宽不能超过车身宽度加 0.10 m；后甲板、腰线、尾门下缘与后车顶之间须保留正高度差。每个构型提供一组可运行预设，建议从预设小幅修改。

车宽输入控制车身基面；包含后视镜、后肩外扩等的实际总包络宽度由生成后的测量报告给出。名义底板高度也不等于整车最小离地间隙。

### 70 个精细造型系数：当前为 Python/API 能力

`fine_shape` 是长度必须为 70 的可选数值数组，每个系数范围为 −0.22…+0.22。它在 7 个纵向站位与 3 个高度层上定义连续造型场，保留轮拱附近的保护过渡。当前 MiShape 界面没有这 70 个系数的专用滑块，不能把它们算作已经交付的界面控件。

| 数组索引（从 0 起） | 含义与单位 |
| --- | --- |
| 0–20 | 7×3 个纵向位移系数，m |
| 21–41 | 7×3 个横向缩放系数，无量纲；作用于原 Y 坐标 |
| 42–62 | 7×3 个竖向位移系数，m |
| 63–69 | 7 个横向冠高系数，m |

生成器会保留输入配方、版本与哈希供重放。相同输入和版本生成相同几何；`seed` 被记录，但单独改变生成配方的 seed 不会注入隐式随机造型。批量探索的 seed 则真实控制参数采样。

## 变体组合

批量功能以当前基准模型和塑形配方为中心，选择 17 个驱动中的一个或多个参数进行分层采样；它不是同时随机更换生成器的五种构型。生成器输出同样可以成为批量塑形的基准。

界面/API 每批 1–50 个变体，同一时间只接受一个运行中的批量任务。探索幅度按参数允许区间的宽度缩放，在当前参数值周围采样，并裁切到合法范围；靠近边界时可能有多个样本被裁切到相同值，不保证全部结果互不重复。相同基准、参数、控制点、选定参数顺序、seed 和软件版本可重放同一批次。

任务运行中逐个显示缩略图及进度，点击变体可以应用其配方继续编辑。停止任务会保留已经完成的变体供当前会话查看；完整 ZIP 下载在全部完成后提供。

完成后的 ZIP 包含：

- `manifest.json`：种子、采样方式、幅度、参数选择及每个变体的测量/质量记录。
- `base-model.json`：用于重放的基准模型。
- 每个 `VAR-xxx/vehicle.obj`：变体 polygon 模型。
- 每个 `VAR-xxx/recipe.json`：参数、控制点、选项及质量记录。

批量产物保存在本机 `.state`。采样结果会保留质量提示；有限几何检查通过不代表每个变体均可制造或可直接求解 CFD。

## Polygon 数据、LOD 与导出

内置素材准备了三层数据：原始对象控制网格、应用源修饰器后的完整网格、用于交互的 viewport LOD。后两者的 polygon 数量可以不同。

日常打开内置素材时，MiShape 载入 `viewport.json`；塑形保持这个载入模型的顶点索引、polygon 索引和组件标签。OBJ 导出保留当前载入模型所携带的 polygon 面。它并不自动把该形变传播到 `fullmesh.json.gz` 或 `source.blend`。源档案留作后续开发高精度映射、纹理处理和 Blender 回写的基础。

原始归档保留源对象、UV、材质、对象世界变换与修饰器描述，同时保留未加入设计包络的阴影平面、隐藏参考物体、重复 clearcoat 外壳和 930 天线。原始输入目录未被修改。

| 格式 | 当前导出行为 |
| --- | --- |
| OBJ | 当前 polygon 面和 `g` 组件分组；不带 UV/MTL/图像纹理 |
| GLB | 当前三角化几何、组件节点和组件基色；当前运行时导出不保留原始图像纹理/UV |
| STL | 三角化表面；数值采用米制，文件本身不存单位或组件材质 |
| PLY | API 支持几何导出；当前导出对话框没有对应按钮 |
| JSON 工程 | `base_model` 与 `recipe`，可以重放编辑；不是 CAD/B-rep 文件 |

只有几何导出适用「仅导出选中组件」。JSON 始终保存整个基准模型与配方。导入已导出的几何文件会把结果视作新基准；重新导入 JSON 工程则可继续调整原来的参数。

素材文件夹额外提供离线生成的 `model.glb`，它与应用的「当前设计 GLB 导出」不同：离线 GLB 使用完整网格，并保留源中存在的 UV 和近似 PBR 材质。所有原始图像纹理独立保存，但当前查看器显示材质基色、粗糙度和金属度，尚未应用这些纹理图。内部几何、OBJ/STL 使用 Z-up；应用导出的 GLB 自动转换为 glTF 标准 Y-up，导入 GLB 时界面默认选择 +Y 向上。素材档案中的离线 model.glb 保持 Z-up，如直接打开该原始档案需在下游按坐标约定转换。

## 几何检查与当前边界

塑形检查包括有限数值、相对源模型新增的退化三角面、法线翻转、最大/RMS 位移、拓扑索引保留及轮组刚性误差。源模型原有退化面单独计数。底面穿过 Z=0 会产生提示。

生成器提供自身的曲面筛查和质量报告，并标识 `production_ready=false`。当前没有完整自交检查、组件间隙/装配验证、壁厚、公差、真实悬架运动学、制造约束、碰撞法规验证、风洞实验或 CFD 认证。组件组成的表面不等于已布尔合并的封闭实体；导出 STL 不代表模型已经可打印。

自动关键点来自已知素材、命名组件或几何启发式；对不同车辆构型仍需人工复核。当前任意车模导入没有提供全自动轮胎/门/灯等零件识别，玻璃、进气口与装饰件的外观不构成真实光学或通流结构。

## 接口与二次开发

本地 FastAPI 的接口说明位于 [http://127.0.0.1:8010/docs](http://127.0.0.1:8010/docs)。主要接口如下：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/health` | 产品、版本与服务状态 |
| `GET /api/bootstrap` | 素材目录、17 参数 schema、生成 schema/预设 |
| `POST /api/models/open` | 按 `asset_id` 打开内置车 |
| `POST /api/import` | multipart 文件导入与单位/坐标标定 |
| `GET /api/models/{id}` | 读取基准模型、测量和控制笼 |
| `POST /api/models/{id}/deform` | 按配方得到更新顶点、测量、质量与控制笼 |
| `POST /api/generate` | 按构型与尺寸生成车辆并保存为基准模型 |
| `POST /api/models/{id}/export` | 导出当前设计或选中组件 |
| `POST /api/batches` | 发起分层采样批次 |
| `GET /api/batches/{id}` | 读取批次状态和已完成配方 |
| `POST /api/batches/{id}/cancel` | 停止后续变体生成 |
| `GET /api/batches/{id}/variants/{index}` | 读取指定已完成变体的顶点与记录 |
| `GET /api/batches/{id}/download` | 下载已完成批次 ZIP |

塑形配方示例；这里 `total_length` 是 mm，控制点 `delta` 是 m：

```json
{
  "parameters": {"total_length": 120, "windscreen_angle": 2, "ride_height": 15},
  "controls": [{"id": 35, "delta": [0, 0, 0.012]}],
  "options": {"symmetry": true, "preserve_wheels": true}
}
```

在项目根目录通过 Python 使用生成器：

```python
from mishape.generation import generate

model = generate({
    "body_style": "fastback",
    "parameters": {"length": 4.94, "width": 1.97},
    "fine_shape": [0.0] * 70,
})
print(model["metadata"]["recipe"])
```

JSON 工程的基本结构是：

```json
{
  "schema": "mishape-project-v1",
  "name": "My design",
  "base_model": {"vertices": [], "faces": [], "polygons": [], "face_labels": [], "parts": [], "metadata": {}},
  "recipe": {"parameters": {}, "controls": [], "options": {"symmetry": true, "preserve_wheels": true}}
}
```

上面空数组仅说明字段结构；实际导入要求包含有效三维模型。基准顶点采用扁平 XYZ 数组，`faces` 为三角面扁平索引，`polygons` 为每个面的顶点索引列表，`face_labels` 对应 `parts[].id`。模型坐标为米。参数 schema 是应用可接受范围的唯一来源。

## 验证与维护

已提供真实素材、几何内核、生成器和 HTTP 集成测试。开发验证需要另外安装 `pytest` 与 `httpx`：

```sh
.venv/bin/python -m pytest mishape/tests -q
```

测试覆盖源 polygon/UV 保留、轮组标识与接地、控制笼、零形变、参数作用、配方重放、生成器约束、导出和批量接口等。交付时的最终测试结果和界面截图以主任务的交付记录为准；这里不将单次测试通过等同于无限车型/参数空间的完整验证。

素材离线转换见 `mishape/scripts/prepare_assets.py` 和 `export_assets_glb.py`；转换才需要 Blender Python 运行时，日常使用不需要。两辆素材的来源和 SHA-256 信息保存在各自原始档案中。素材由用户提供，本地处理不自动授予再分发授权。

## 生成参数的关联尺寸

界面默认启用「自动联动关联尺寸」。只在保持布局有效所必需时调整车顶控制段、轮距或前悬占比，并显示实际联动值；保存配方与滑块会同步更新。用户正在编辑的字段不会被悄悄改回其他数值。无可行解或涉及多处结构冲突时明确拒绝，保留上一次可用模型。关闭此选项后可独立输入参数，但仍需通过生成器的布局约束。

## OBJ 原生多边形约定

OBJ 支持原始四边形和凹多边形，显示面采用确定性耳切三角化；非平面面片选择简单轴向投影，并在 metadata 中记录三角化约定与数量。源 polygon 索引不会被替换成三角面索引。自交或无法得到简单投影的面明确拒绝。930 车辆导出再导入，66,245 个顶点和 65,220 个原始 polygon 的索引逐项保留。界面线框显示渲染三角边。OBJ 的 UV/原法线引用可以读入工程，当前查看器和运行时 OBJ 导出尚不使用这些源 UV/法线。

## 本次实际验证

64 项 Python 测试、13 项 JavaScript 测试通过。已在本机 Chrome 中完成真实模型的滑块、控制点拖动、撤销/重做、双视图、组件隔离/展开、工程重放、尺度校准、12 辆组合生成/下载/继续编辑，以及 5.1 m SUV 参数生成与导出。软件 WebGL 测试中的一次滑块端到端更新约 0.41 秒，持续拖动期间也会展示中间结果；不承诺所有设备固定帧率。

详细证据位于 `docs/verification/`：测试汇总、浏览器报告、OBJ/GLB 往返报告和界面截图。12 个真实变体与生成 SUV 的示例文件随发布包的 `examples/` 提供。

无独立轮胎组件名称的整体 STL 等模型，当前不会可靠地自动分割出轮组；界面保留刚性选项，但质量报告会注明未识别轮组、刚性未验证。此类模型应先在上游拆分命名轮组，或使用已分组的 OBJ/GLB。
